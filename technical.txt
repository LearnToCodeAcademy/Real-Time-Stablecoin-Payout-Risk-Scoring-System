REAL-TIME STABLECOIN PAYOUT RISK SCORING SYSTEM
TECHNICAL ECOSYSTEM MAP

Credit: John Marwin Ebona

This file explains how the repository fits together as an ecosystem. It is
intentionally long and explicit. The README is the compact front door; this
file is the engineering map.

===============================================================================
1. SYSTEM PURPOSE
===============================================================================

The system is a Python-based wallet risk intelligence engine for stablecoin and
token payouts. Its goal is to evaluate a wallet before or during payout and
return a practical operational decision:

- ALLOW: payout can continue.
- REVIEW: suspicious signal exists and a human should review.
- BLOCK: high-risk malicious or poisoned wallet behavior was detected.

The system does this by combining:

- Etherscan transaction collection.
- Dataset generation across multiple data versions.
- Token-aware feature engineering.
- RandomForest / XGBoost / LightGBM model training.
- Runtime rules for obvious high-risk behavior.
- Lazy model loading at inference time.
- Graph intelligence from wallet-to-wallet transaction networks.
- FastAPI service endpoints.
- Streamlit dashboard views.
- WebSocket listener scaffolding for live token-transfer monitoring.

===============================================================================
2. HIGH-LEVEL DATA FLOW
===============================================================================

The current source-level flow is:

1. main.py talks to Etherscan and wallet seed/pool files.
2. main.py expands wallets and writes versioned CSV datasets.
3. train_ml.py reads those CSV datasets and trains token-specific models.
4. train_ml.py exports models, scalers, and feature lists as pickle files.
5. wallet_check.py fetches wallet transactions at runtime.
6. wallet_check.py detects the token and generates scoring features.
7. wallet_check.py applies defensive rules before ML.
8. wallet_check.py lazily loads the right token model when needed.
9. wallet_check.py returns ALLOW, REVIEW, or BLOCK.
10. api.py exposes this through HTTP endpoints.
11. dashboard.py offers an operator-facing Streamlit surface.
12. stream_listener.py can listen to provider WebSockets and pass events into
    scoring handlers.
13. graph_engine.py can enrich either dataset generation or runtime scoring
    with network metrics.
14. db.py optionally caches features and labels in Postgres.

ASCII architecture:

    Etherscan API
        |
        v
    main.py ----------------------.
        |                         |
        v                         v
    datasets/*.csv             graph_engine.py
        |                         |
        v                         |
    train_ml.py                   |
        |                         |
        v                         |
    models/*.pkl                  |
        |                         |
        v                         |
    wallet_check.py <-------------'
        |
        +--> api.py
        +--> dashboard.py
        +--> stream_listener.py callback path

===============================================================================
4. DATASET VERSIONING
===============================================================================

main.py defines a V0-V4 dataset lifecycle:

V0 - broad baseline safe candidates
    Intended to represent normal-looking wallets and broad background behavior.

V1 - high-trust malicious
    Seed-driven malicious or suspicious wallet expansion.

V2 - scaled malicious
    Larger malicious expansion from configured seeds or pools.

V3 - poisoning behavior
    Focuses on address poisoning and suspicious behavioral signatures.

V4 - high-confidence safe
    Filters safe candidates more strictly.

The training pipeline then reads CSV files such as:

- datasets/v0_<token>.csv
- datasets/v1_<token>.csv
- datasets/v2_<token>.csv
- datasets/v3_<token>.csv
- datasets/<token>_labeled_v4.csv
- datasets/<token>_training_ready.csv

The current clone does not include an active datasets/ folder in the file list,
but it does include historical CSVs under "datasets deprecated/" and several
small backup CSVs under backups/.

===============================================================================
5. RUNTIME DECISION FLOW
===============================================================================

wallet_check.py is the center of runtime inference.

Main runtime steps:

1. fetch_transactions(address, debug=False)
   Calls Etherscan for a wallet address and returns transaction data.

2. detect_token(transactions, manual_token=None, debug=False)
   Uses a three-level strategy:
   - manual token override when provided;
   - tokenSymbol from transaction data;
   - contractAddress mapped against known token contracts.

3. generate_features(transactions, wallet_address=None)
   Converts raw transactions into model/rule features.

4. apply_rule_based_filters(...)
   Applies defensive heuristics before ML. If a rule confidently decides, it
   can return ALLOW, REVIEW, or BLOCK without model inference.

5. load_model_for_token(token)
   Loads a token model only when that token is being scored. This avoids loading
   all model files during import/startup.

6. score_wallet(address, manual_token=None, debug=False)
   Orchestrates the full scoring lifecycle and returns a dictionary-like result.

Output fields used by api.py include:

- wallet
- token
- score
- decision
- reason
- prob_normal
- prob_malicious
- prob_poisoned
- confidence
- graph_degree
- graph_pagerank
- connected_to_malicious
- features_extracted
- timestamp
- processing_time_ms

9. TRAINING ECOSYSTEM
===============================================================================

train_ml.py uses the following concept:

For each token:
    1. Load available datasets.
    2. Merge safe, malicious, poisoned, and unknown rows.
    3. Build feature matrix using ALL_FEATURES.
    4. Scale features with StandardScaler.
    5. Oversample risk classes.
    6. Split into train/validation.
    7. Train one or more models.
    8. Evaluate with F1 score.
    9. Save best model artifacts.

Model choices:
    - rf
    - xgb
    - lgb
    - auto

Artifacts:
    - models/<token>_model.pkl
    - models/<token>_model_<best_name>.pkl
    - models/<token>_scaler.pkl
    - models/<token>_features.pkl

Important methodology note:
    Validation metrics generated by this current code should be treated as
    development signals, not audited production performance. The pipeline should
    be refactored to split first, then fit scalers and resamplers only on the
    training fold.

===============================================================================
10. GRAPH ECOSYSTEM
===============================================================================

graph_engine.py can convert transactions into a graph where:

- nodes are wallets;
- edges are wallet-to-wallet transfers;
- edge weight is cumulative value;
- edge frequency is transaction count.

Graph features can include:

- node degree;
- PageRank;
- clustering coefficient;
- betweenness centrality;
- closeness centrality;
- unique inbound/outbound counterparties;
- suspicious clusters;
- path distance to known malicious wallets;
- inflow/outflow values;
- transaction flow ratio.

These graph features can enrich:

- dataset generation in main.py;
- runtime scoring in wallet_check.py;
- visualization in dashboard.py;
- future network graph UI work.

12. SECURITY AND PRODUCTION CAVEATS
===============================================================================

This section is explicit because this repository touches payout security.

Hardcoded keys:
    main.py and wallet_check.py now load Etherscan API keys from environment
    variables. Previously exposed keys still require rotation and Git history
    scrubbing before real production use.

Tracked .env:
    .env exists in the clone. It should be removed from tracking and replaced by
    .env.example with placeholders.

Generated artifacts:
    CSV and pickle artifacts are tracked despite .gitignore rules. This can make
    repository history large and can leak sensitive data if datasets contain
    private labels or proprietary wallet sets.

Dependency completeness:
    requirements.txt now includes API, dashboard, graph, and stream runtime
    dependencies. Deep-learning stacks remain optional and should be installed
    deliberately when GNN/LSTM/Transformer work is needed.

Metrics:
    Any accuracy/F1/recall claims should be regenerated with a leakage-free
    train/validation/test process before being used in production documents.

14. SHORT MENTAL MODEL
===============================================================================

Think of the system as five connected machines:

1. Collector:
    main.py gathers and expands wallet data.

2. Trainer:
    train_ml.py turns datasets into token models.

3. Scorer:
    wallet_check.py turns one wallet into one decision.

4. Server:
    api.py turns scorer logic into HTTP endpoints.

5. Operator surfaces:
    dashboard.py, stream_listener.py, and index.html help humans view or operate
    the system locally.

Everything else either stores data, stores models, documents historical fixes,
or tests one part of those machines.
